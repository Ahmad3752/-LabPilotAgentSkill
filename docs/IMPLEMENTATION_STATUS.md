# Implementation status

This file is the source of truth for what has been **verified**, what is **implemented but not yet verified**, and what is **out of scope**. README claims must match it.

Last updated: 2026-11-27.

## Phase scope

This phase targets **Google Colab labs only**. Docker, local Spark/Java runtimes and other heavy local profiles were removed on purpose. A lab's own Colab setup cells (`!pip`, `apt-get`, Hadoop or PySpark installs) run inside Colab. The plain local Jupyter kernel remains only as a clearly labelled fallback.

## Verified (real runs on Windows 11 + Python 3.11/3.12, VS Code)

| Capability | How it was verified |
|---|---|
| Reading `.docx` manuals | Covered by unit tests on synthetic manuals and the real course Lab 8 manual. Verified behaviours: reading order, nested tables, stable anchors with fingerprints, Task / Part / "Question N" units, one "Your answer:" box per question, fill-in tables, starter code, questions, student fields, embedded images, Colab-specific starter code. |
| Dataset handling | Unit tests cover discovery, matching, hashing and schema checks: exact, case-insensitive and alias matches, ambiguous and missing files, corrupt files, schema mismatch, encodings, path traversal. |
| Plan, cells and answers validation | Unit and integration tests cover duplicate IDs, task order, dependency order, anchor fingerprints, grounded answers (cited cells must have passed) and fill-in table values. |
| Local kernel (tests and offline demo only) | Since 2026-11-27 lab code runs only on Google Colab: `auto` means colab-cli and `local` is refused unless `LABPILOT_ALLOW_LOCAL=1` (set by the tests and `examples/run_demo.py`). Not signed in to Colab stops with AUTH_REQUIRED and `labpilot colab-login`. Integration tests with a real kernel cover a persistent kernel per attempt, per-cell checkpoints, stop at the first error, repair → stale invalidation → replay, the retry budget, a hard wall-clock timeout (a Windows kernel interrupt alone did not stop `time.sleep`; found and fixed), output size limits and credential-scrubbed environments. |
| Recovery | Integration tests cover: cancel while running → `CANCELLED` → resume; abrupt kill of the whole process tree → stale lock recovered → resume; changed inputs detected → resume re-stages; missing dataset → `PARTIAL` → user adds the file → resume → `COMPLETED`. |
| Screenshots | Real headless Chromium element screenshots of the actual executed notebook. Scripts are stripped, JavaScript is disabled, the network is blocked and images are cropped to their content. Long outputs are split at line, row or image boundaries. Blank or undecodable images are detected. Each image has provenance and a sha256. Checked visually. |
| Word output | The original is never modified, and output is regenerated from it each time, so there is no duplication. Placeholders are removed but labels are kept. Exact-height and can't-split rows are relaxed. Images are inline and sized to the cell. Fill-in table cells are written. Structural validation checks text order, screenshots embedded byte for byte, original images, headers/footers and page setup. The `Completed` / `Partial` naming follows the completion contract. |
| Optional page rendering | Microsoft Word, run locally through COM (read-only, `-EncodedCommand`, no execution-policy change), converts to PDF and each page is rendered with `pypdfium2`. Pages were checked visually. LibreOffice is used when installed (not tested here). |
| **Google Colab via the official `google-colab-cli` 0.8.0, natively on Windows** | Steps verified on real Colab: sign-in with `labpilot colab-login`, CPU runtime allocation, dataset upload with remote sha256 check, per-cell execution with rich outputs (charts included), success decided from the output objects (the CLI exits 0 even on errors), screenshots, Word export, and release of the owned session ("No active sessions" afterwards). The synthetic sample lab completed with identical answers on Colab and on the local fallback. |
| **Real course lab on Google Colab (Hadoop, 3 tasks / 9 questions)** | A real university manual (Hadoop MapReduce/YARN, continuing an earlier lab) was run end to end on Colab: environment setup from the earlier manual, all TODOs, counter/split tables filled from real job counters, grounded answers, teardown, Word export. Running it found and fixed: 'Question N' sections, per-question answer boxes, fill-in tables, numbered '...? Explain.' questions, header/footer false positive, over-broad delete rule, Hadoop Streaming output naming (cells that 'passed' while checking nothing), missing closing section. Not checked against the instructor's marking. |
| Colab check (`colab_fit` in `init`/`inspect`, `labpilot colab-check`) | Decides from the manual whether a lab can be done in Colab and gives the reason. Checked on 11 real CS-412 manuals (2026-11-27): Labs 1–4 and 7–10 (Python, Pandas, Hadoop, Spark on Colab) pass; Labs 5–6 (AWS console, EC2, SSH) and Lab 11 (Kafka in Docker, tmux terminals, Killercoda) are refused with the right reasons. Unit-tested on synthetic text; the skill tells the agent to confirm the verdict and stop on a refusal. |
| Quality evaluator (`labpilot evaluate`) | Unit-tested; part of export: fails on log-like answers, error text inside passed outputs, empty fill-in tables, parts without evidence, sections the introduction promises but nothing covers. The skill adds an independent reviewer step with a rubric. |
| Colab CLI installer | `labpilot setup --backend colab-cli --install-colab-cli` installs into a LabPilot-owned venv. It needs a **signed** Python 3.12+, because Windows Smart App Control blocks unsigned builds such as uv-managed Python; this is detected and explained. |
| Windows installer (`scripts/install.ps1`) | Clean install verified 2026-11-27 into an empty install root: finds Python 3.12, creates the venv, installs LabPilot with the `[lab]` extras, writes the `labpilot.cmd` shim, installs Chromium and the Codex skill, and `doctor` passes. On a fresh Windows PC PowerShell blocks scripts by default, so the README runs it with `powershell -ExecutionPolicy Bypass -File`, which changes no settings. Since 2026-11-27 the script also runs `colab-login`, `labpilot lms connect` and then starts the agent in `-ProjectDir` with the first prompt. **Not yet verified:** that full one-command run on a clean PC. |
| Skill packaging | One canonical `skills/labpilot/SKILL.md`, which follows the Agent Skills spec. Copies are installed to `.agents/skills` (Codex) and `.claude/skills` (Claude Code) with an ownership marker and a hash. Reruns are idempotent, and user-created skills are never overwritten. |
| Security screening | Unit tests: deny rules (credentials, environment dumps, `files.upload()`, `input()`, Drive mounts, deleting root, home or system folders) and warn rules (shell, network, absolute paths). Secret redaction is also tested. |

## Implemented, not yet verified

| Capability | What is missing |
|---|---|
| Colab MCP (browser) bridge | The protocol is tested: host actions, then strict validation and ingest of host-reported outputs. It has not been tried with the real `colab-mcp` server, which needs registration in Claude Code and a connected Colab tab. Codex is not a documented colab-mcp client. |
| Codex: running LabPilot from inside the agent | Codex's Windows sandbox cannot read per-user installs (Python, the LabPilot venv, the Colab sign-in), so `labpilot` failed inside Codex and the first real Codex run (Lab 2, 2026-11-27) took 35 minutes and 5 user commands. Verified by hand in a real Codex 0.169 session: a LabPilot-owned `~/.codex/rules/labpilot.rules` (`allow` for `labpilot` and the venv `python -m labpilot`) plus the "Approve for me" mode (`approval_policy = "on-request"`, `approvals_reviewer = "auto_review"`) plus `require_escalated` ran `labpilot doctor` as the user with no prompt. `labpilot setup` now writes the rules file, the project `.codex/config.toml` keys and Claude Code allow rules, and `uninstall` removes them; verified with unit tests, `codex execpolicy check` and `codex debug prompt-input` (the project config applies only when the folder is trusted). **Not yet verified:** a full lab in Codex after `setup`, and whether a mode saved with /permissions overrides the project config. |
| `labpilot finish` (one command after plan/cells/answers) | Runs build → execute → capture → answers → export/evaluate, skips steps whose results are current, resumes without re-sending unchanged failed cells, returns one JSON verdict. Colab runtime release is reported only when `colab stop` succeeded (otherwise release-pending, retried by `cancel`). Verified with unit tests against a labelled fake Colab CLI and the offline demo (COMPLETED; a repeat `finish` skips every step). **Not yet verified on real Colab.** |
| Manual structure fixes (2026-11-27, from the real Lab 2 run) | "Activity N.M" is a child of Task N (Lab 2: 12 tasks with duplicate ids → 5 tasks, 7 activities); `Q1.`-labelled instructions are questions (0 → 15); files the lab's own code creates (`to_csv`, `sqlite3.connect` + `CREATE TABLE`, `open(..., 'w')`) are `generated_files`, not required inputs; no doubled "Task 2: Task 2" headings; `colab_fit` blocks Microsoft SQL Server/SSMS (Lab 1) and lists `files.upload()`/`drive.mount(` under `needs_attention` (Labs 9, 10). Checked on the real Labs 1–11 manuals; unit tests on synthetic manuals. Tall code cells are captured as several real screenshot parts split at source-line boundaries ("part 1 of 2"); integration-tested with real Chromium. |
| Ask once, then run (skill, 2026-11-27) | At discovery the skill runs `labpilot doctor --json` and `colab-check`, sends one message (lab, Colab verdict, Colab sign-in, "yes + name + CMS ID"), ends its turn, and after the yes asks nothing more, posting a status line with a percentage per phase. Added after a Codex Lab 3 run that asked mid-work and then waited at CONSENT_REQUIRED. The skill also has *How to write* rules (student voice, answer first, rounded numbers, plain-text formulas, no meta or setup sections, library deprecation warnings silenced). **Not yet verified** in a real Codex or Claude Code run. |
| Saved student name / CMS ID | `labpilot init --student-name X --student-id Y` saves them in the user config (`config.json`, `student` key; local only) and every later `init` reuses them; new values overwrite. Synthetic runs never use or save them. `labpilot doctor --json` reports `student: {name, id}` or `null`. Unit-tested (`tests/unit/test_student_profile.py`). |
| Claude Code skill discovery | Installed to `.claude/skills/labpilot`. Not exercised in a separate session. |
| macOS / Linux install scripts | Written (`scripts/install.sh`). Not run on a real Mac or Linux machine. |
| New-lab checks through the Nuts LMS MCP (`labpilot lms check / stage / mark / list`) | Host-mediated and read-only: the agent calls the `moodle-mcp` tools and passes their JSON to LabPilot, which never logs in or submits. **Verified so far:** `moodle-mcp` (commit b4aa67a, source reviewed) installs with `uv tool install`; its MCP server starts over stdio and lists its 15 tools with the parameters read from the source; Claude Code registration reports Connected; tool calls without a login return the "No credentials" error; unit tests cover classification, status, ledger, staging, provenance and doctor on synthetic payloads shaped like the tool output. On Windows, Smart App Control blocks uv's unsigned `moodle-mcp.exe`, so it runs as `<tool python> -m moodle_mcp`. The NUST LMS server needs legacy TLS renegotiation, which `moodle-mcp` (b4aa67a) does not enable, so every call failed with `UNSAFE_LEGACY_RENEGOTIATION_DISABLED`. Workaround verified 2026-11-27 with a real signed-in account: login, course list, and the full read-only check through the MCP tools (`whoami` → `list_assignments` → `labpilot lms check` → `assignment_status` → check with `--status`) classified 19 real assignments correctly (1 new lab, including the unspaced name "Lab11", 10 closed, 8 not labs). LabPilot ships `lms_openssl.cnf` and `doctor` prints the registration command with `OPENSSL_CONF`. `labpilot lms connect` runs the missing steps itself (uv tool install, moodle-mcp's own login prompt in the user's terminal, registration with Codex and Claude Code at user scope); unit-tested with a fake subprocess layer, not yet run on a clean PC. A one-line upstream fix was prepared as a PR; remove the workaround once it is merged. **Not yet verified:** real downloads (`download_file`, `lms stage`), and a full lab run started from an LMS download. |

## Known limitations (by design or upstream)

- Screenshots are renderings of the executed notebook, not captures of the Colab web UI. A manual that demands Colab UI screenshots is reported as unmet.
- The Colab CLI does not report Jupyter execution counters, so code screenshots show `In [ ]:`. LabPilot leaves them blank rather than inventing numbers.
- The local fallback isolates packages but not filesystem privileges.
- Labs that continue an earlier lab (for example Lab 8 needs Lab 7's setup) need that earlier manual, or its setup code, in the run.

## Out of scope in this phase

Running the Colab CLI through WSL (removed 2026-11-26: native Windows works, so the untested WSL path was deleted), LMS submission and any LMS write, WhatsApp or other messaging, scheduled jobs (including background new-lab polling), Docker and local Spark/Java profiles, native Colab UI capture.
